  Root cause of the earlier depth-7-11-vs-21 anomaly: explore_benchmark() previously wrapped
  its DFS in an outer `for (int max_depth = 0; max_depth <= search_depth; max_depth++)` loop
  that reset the stack and `visited` set from scratch on every iteration -- an iterative-
  deepening restart that bmark-3's explore_benchmark() does not have (it runs one continuous
  DFS with a single `visited` set to the search_depth cap). That extra loop was a benchmark-
  harness bug introduced when bmark-4's explore_benchmark() was written, not a property of the
  solver: it forced repeated re-exploration of the same shallow states at every outer
  iteration, consuming the 10s budget without ever reaching a deep, single DFS pass. It has
  been removed so explore_benchmark() now matches bmark-3's single-pass structure. Separately,
  move/inverse round-trip tests (R,R',L,L',U,U',D,D',F,F',B,B' from solved) confirmed the
  bit-shift corner/edge encoding returns to the exact solved long values bit-for-bit after
  every move+inverse pair, so no evidence of a canonicalisation or hashing bug was found.
  Either way, raw states/sec is only one proxy for whether this branch's bit-shift/long state
  representation was a successful optimisation. This benchmark's actual intent per the bmark-4
  commit was correctness of the bit-shift representation, not exploration throughput -- the
  real payoff of two `long`s over two `vector<pair<int,int>>`s (no per-move heap allocation)
  shows up in memory/allocation overhead during real solves, which this synthetic exploration
  benchmark does not directly measure.
